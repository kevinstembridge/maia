# Job Execution History Page — Design

## Goal
Add a job execution history page to `libs/maia-ui-workspace/projects/maia-jobs`, backed by a new paginated/filterable backend endpoint, showing every past (and currently running) job execution — one card per row, not a table.

## Background
- The existing `maia-jobs` dashboard (`jobs-dashboard-page.component.*`) only ever shows *current* state: jobs currently running (in-memory, `MaiaJobService.runningJobs`) plus, per job, up to 10 *recent failures* (`JobStateResponseDto.recentlyFailedExecutions`, sourced from `JobExecutionRepo.recentFailedExecutions`). There is no way to see successful executions, or failures beyond the 10-most-recent-per-job cap, or to browse/filter execution history at all.
- Every execution (running, succeeded, or failed) is already persisted as a `JobExecutionEntity` (`completionStatus`, `startTimestamp`, `endTimestamp`, `errorMessage`, `invokedBy`, `metrics`, `stackTrace`) — `completionStatus` is `null` while a job is still running, `SUCCESS`/`FAILED` once it finishes. This is generated from `MaiaJobSpec.kt`'s `jobExecutionEntityDef` (`libs/maia-job-parent/maia-job-spec`).
- The generated DAO (`JobExecutionDao`, `libs/maia-job-parent/maia-job-dao`) already supports everything needed for server-side paging and filtering: `findAllBy(filter, pageable)` (sort/limit/offset) and `count(filter)`, plus a `JobExecutionEntityFilters` builder (`eq`, `in`, `gte`/`lte`, `isNull`/`isNotNull`) generated per-entity. Its `contains` operator is unimplemented (`TODO("Not implemented yet")`) — a job-name filter therefore uses exact match, not substring search, to avoid touching that shared generator code.
- A generic, already-existing `SearchResultPage<T>` (`libs/maia-domain/.../search/SearchResultPage.kt`: `results`, `totalResultCount`, `offset`, `limit`) is the pagination envelope. This is a hand-written general-purpose class, unrelated to the framework's much larger generated "searchable blotter"/ag-grid subsystem (`SearchableDtoRepoRenderer`, `EntityHistoryBlotterSearchServiceRenderer`, etc.) — that subsystem is for fully generated CRUD-entity blotter pages and is the wrong tool here, since `maia-jobs` is a hand-written library consuming a hand-written `MaiaJobService`/`MaiaJobEndpoint`, not generator output. Using `SearchResultPage<T>` directly keeps this change proportionate.
- Response DTOs in this module (`JobStateResponseDto`, `JobExecutionSummaryResponseDto`, etc.) are generated via `simpleResponseDto(...)` in `MaiaJobSpec.kt`, not hand-written. **The generator emits constructor parameters in alphabetical order by field name, not declaration order** (confirmed in a prior design pass on this same module) — this applies to the new DTO below too.
- No date-range picker (`mat-datepicker`) exists anywhere yet in `libs/maia-ui-workspace` or `maia-showcase` — this is the first use in the codebase. `provideNativeDateAdapter()` is already configured at the showcase app root (`app.config.ts`), so no new app-level wiring is needed.
- The existing dashboard has no `ReactiveFormsModule` usage anywhere — filtering is done with plain `(input)` event handlers over signals. The history page filter bar follows that same style (two independent `mat-datepicker` single-date inputs for "From"/"To", not a `mat-date-range-input`, which requires a `FormGroup`) rather than introducing reactive forms for one filter row.
- `JobMetricsDialogComponent` and `StacktraceDialogComponent` (both already in `maia-jobs`) take plain `any`/`string` data via `MAT_DIALOG_DATA` — no changes needed to reuse them from the new history cards.

## Behavior

### Backend
- **Spec** (`MaiaJobSpec.kt`): add `jobExecutionHistoryItemDtoDef = simpleResponseDto("org.maiaframework.job", "JobExecutionHistoryItem")` with fields `jobExecutionId` (domainId), `jobName`, `invokedBy`, `startTimestamp`, `endTimestamp` (nullable), `completionStatus` (nullable — `jobCompletionStatusEnumDef`), `errorMessage` (nullable), `metrics` (`mapOfStringToAny`). Regenerate via `./gradlew :libs:maia-job-parent:maia-job-domain:maiaGeneration`, producing `JobExecutionHistoryItemResponseDto` with constructor params in alphabetical field-name order: `(completionStatus, endTimestamp, errorMessage, invokedBy, jobExecutionId, jobName, metrics, startTimestamp)`.
- **`JobExecutionRepo`**: new method, e.g. `searchExecutionHistory(jobName: JobName?, status: String?, from: Instant?, to: Instant?, offset: Int, limit: Int): SearchResultPage<JobExecutionEntity>` (`status` is the raw `"RUNNING"|"SUCCESS"|"FAILED"` string passed through from the endpoint — no new enum/sealed type introduced just for this):
  - Build a list of optional `JobExecutionEntityFilter`s: `filters.jobName eq jobName` (if given), `filters.completionStatus eq status` for `SUCCESS`/`FAILED`, `filters.completionStatus.isNull()` for `RUNNING`, `filters.startTimestamp gte from` / `filters.startTimestamp lte to` (if given).
  - Combine with `filters.and(*conditions.toTypedArray())` when non-empty, else `JobExecutionEntityFilters.NoopFilter()` (already generated, used for the "no filter" case) — `and()` with zero args would produce an empty/invalid `WHERE` clause.
  - Sort `Sort.by(Sort.Order.desc(JobExecutionEntityMeta.startTimestamp))`, `PageRequest.of(offset / limit, limit, sort)`.
  - Return `SearchResultPage(jobExecutionDao.findAllBy(filter, pageRequest), jobExecutionDao.count(filter), offset, limit)`.
- **`MaiaJobService`**: `searchJobExecutionHistory(...): SearchResultPage<JobExecutionHistoryItemResponseDto>`, mapping each `JobExecutionEntity` to the new DTO (`SearchResultPage.results.map { ... }`, preserving `totalResultCount`/`offset`/`limit`).
- **`MaiaJobEndpoint`**: `GET /job/execution_history?jobName=&status=&from=&to=&offset=&limit=`, `@PreAuthorize("hasAuthority('MAIA_JOB_READ')")`, all query params optional except sane defaults for `offset` (0) and `limit` (20). `status` is a plain `String?` (`"RUNNING" | "SUCCESS" | "FAILED"`, case-sensitive) — `RUNNING` isn't a real `JobCompletionStatus` enum value, so the endpoint maps it to the "is null" filter case rather than parsing it as the enum. `from`/`to` are ISO-8601 instant strings (`Instant.parse(...)`), computed as day-boundaries on the frontend (see below) so the backend does no timezone math.

### Frontend (`libs/maia-ui-workspace/projects/maia-jobs`)
- **Models**: `JobExecutionHistoryItem.ts` (`jobExecutionId, jobName, invokedBy, startTimestamp, endTimestamp: string | null, completionStatus: 'SUCCESS' | 'FAILED' | null, errorMessage: string | null, metrics: any`); `SearchResultPage.ts` (`results: T[], totalResultCount: number, offset: number, limit: number`), a generic interface mirroring the backend envelope.
- **`JobsApiService`**: `searchJobExecutionHistory(criteria: {jobName?, status?, from?, to?, offset, limit}): Observable<SearchResultPage<JobExecutionHistoryItem>>`, built with `HttpParams`, hitting `GET {baseUrl}/job/execution_history`. Same `catchError` pattern as the other methods, falling back to an empty page (`{results: [], totalResultCount: 0, offset: 0, limit}`) on error.
- **`job-history-filtering.ts`** (pure functions, mirrors `jobs-filtering.ts`):
  - `deriveHistoryStatus(item): 'running' | 'success' | 'failed'` — `item.completionStatus === null ? 'running' : item.completionStatus.toLowerCase()`.
  - `formatDuration(startTimestamp, endTimestamp): string` — `endTimestamp === null` → `'Running…'`; otherwise formats `endTimestamp - startTimestamp` using the same `<Ns>` / `<Mm> <Ss>` / `<Hh> <MMm>` rules as the dashboard's existing `formatElapsed` (separate implementation — fixed duration, not "elapsed since now").
  - `.spec.ts` covering both functions' branches, mirroring `jobs-filtering.spec.ts`.
- **`JobHistoryStore`** (new `signalStore`, mirrors `JobsDashboardStore`'s shape but no polling): state `{items: JobExecutionHistoryItem[], totalCount, isLoading, error, jobNameFilter: string | null, statusFilter: 'RUNNING'|'SUCCESS'|'FAILED'|null, fromDate: string | null, toDate: string | null, pageIndex, pageSize, availableJobNames: string[]}`. An `rxMethod` refetches whenever filters or page change (debounced/switchMap'd the same way as the existing store's fetch pipeline); a separate one-shot load of `availableJobNames` via the existing `JobsApiService.getJobsState()` (mapped to distinct job names) populates the job-name filter dropdown once on init — no new endpoint for this. `onJobNameFilterChanged`/`onStatusFilterChanged`/`onDateRangeChanged` all reset `pageIndex` to 0; `onPageChanged(pageIndex, pageSize)` does not.
- **`JobExecutionHistoryCardComponent`** (`maia-job-execution-history-card`): input `historyItem: JobExecutionHistoryItem`, outputs `displayStackTrace: string` / `displayJobMetrics: any`. Shows a status badge (colored dot + label, extending the dashboard's `STATUS_COLORS`/`STATUS_LABELS` pattern with a `success` entry — green, same color currently used for `idle`), job name, invoked-by, formatted start/end timestamps, `formatDuration(...)`, and for failures: the error message plus a "View stacktrace" button (parent resolves it via the existing `JobsApiService.getStacktrace` + `StacktraceDialogComponent`, same flow as today's dashboard). A "View metrics" button opens `JobMetricsDialogComponent` directly with `historyItem.metrics` (no extra fetch needed — unlike the running-job case, the metrics are already inline in the DTO here too, matching how the dashboard already does it for `RunningJobStateResponseDto.metrics`).
- **`JobHistoryPageComponent`** (`maia-job-history-page`, new folder `job-history/`): filter bar — job name `mat-select` (options from `store.availableJobNames()`, plus an "All jobs" option), status `mat-select` (`All` / `Running` / `Success` / `Failed`), two `mat-datepicker` inputs ("From"/"To"); a `mat-paginator` bound to `store.totalCount()`/`pageIndex`/`pageSize` (options `[10, 20, 50]`, default 20); content area with the same loading-spinner / error-banner-with-retry / empty-message / list-of-cards structure as the dashboard page: spinner shows only when `isLoading() && items().length === 0`, error banner (with Retry) only when `error() && items().length === 0` — once any page of results has loaded, a subsequent filter/page-change error leaves the last-known list showing rather than blanking it. Cards render as a single-column vertical stack (one card per row, per requirement), not a grid.
- **`JobsDashboardPageComponent`**: add a "View History" button, `routerLink="/jobs-history"` (`RouterLink` import added), next to the existing filter bar — matches the absolute-path convention the showcase app's nav menu already uses for `/jobs-dashboard`.
- **`public-api.ts`**: export the new models, `JobExecutionHistoryCardComponent`, and `JobHistoryPageComponent`.

### Showcase app wiring
- New `maia-showcase/maia-showcase-ui/src/app/pages/job-history/job-history-page.ts`, mirroring `jobs-dashboard-page.ts`: wraps `<maia-job-history-page>` inside `<maia-page-layout pageTitle="Job History">`.
- `app.routes.ts`: add `{ path: 'jobs-history', loadComponent: () => import('./pages/job-history/job-history-page').then(m => m.JobHistoryPage) }`, alongside the existing `jobs-dashboard` route.
- `app.html`: add a "Job History" `mat-menu-item` with `routerLink="/jobs-history"`, next to the existing "Jobs Dashboard" item.

## Out of scope
- No substring/"contains" job-name search — exact match only, since the generated filter DSL's `contains` operator is unimplemented and implementing it is a shared-generator change, not part of this page.
- No live polling/auto-refresh on the history page (unlike the current-state dashboard) — history is browsed on demand; the paginator/filter controls trigger fetches, nothing runs on a timer.
- No new backend tests — `libs/maia-job-parent` has no existing hand-written test sources for `MaiaJobService`/`JobExecutionRepo`/`MaiaJobEndpoint` to extend; adding test infrastructure from scratch for this one endpoint is disproportionate. Verified manually instead (see below).
- No date-range picker component reuse/abstraction — this is a one-off two-field "From"/"To" filter, not a new shared date-range component.
- No changes to the existing recent-failures-on-the-current-dashboard behavior — that stays as-is; this is a purely additive new page/endpoint.

## Verification
- New `job-history-filtering.spec.ts`: `deriveHistoryStatus` for all three states; `formatDuration` for a running item (`endTimestamp === null`) and boundary durations (seconds/minutes/over an hour), matching `formatElapsed`'s existing formatting rules.
- Backend: compile + manual — confirm `GET /job/execution_history` with no params returns the most recent executions across all jobs, newest first; confirm `jobName`, `status` (each of `RUNNING`/`SUCCESS`/`FAILED`), and `from`/`to` filters each narrow the result set correctly in isolation and combined; confirm `offset`/`limit` paging returns the right slice and `totalResultCount` reflects the *filtered* count, not the grand total.
- Manually run the showcase app: navigate to Job History from the nav menu and from the dashboard's "View History" button; confirm cards render one-per-row (not a grid/table); confirm filters + paginator all correctly trigger refetches and reset to page 0 on filter change (but not on page-only change); confirm "View stacktrace" and "View metrics" open the existing dialogs with correct content for a failed and a running/succeeded card respectively; confirm the empty-message state when a filter matches nothing, and the error banner + working Retry when the backend is unreachable.
