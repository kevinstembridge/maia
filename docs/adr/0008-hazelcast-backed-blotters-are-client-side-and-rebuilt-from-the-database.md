# Hazelcast-backed Blotters are client-side and rebuilt from the database

A Searchable DTO can be backed by a Hazelcast map, declared with `hazelcastEnabled(autoRefresh = true)`, as an alternative to SQL (the default) or Elasticsearch. The three backings are mutually exclusive on one Searchable DTO. The map holds the same rich, denormalized row as an Elasticsearch document: [ADR-0007](0007-es-backed-blotters-denormalize-entity-refs.md) applies, and the existing refresh-dependency plan keeps entries fresh after the owning transaction commits, as in [ADR-0004](0004-crud-notifications-delivered-after-commit.md).

A Hazelcast-backed Blotter is a Client-side blotter: one generated endpoint returns the whole set, and AG Grid filters and sorts it in the browser. There is no server-side filter model, paging or infinite scroll, so this is a deliberate exception to [ADR-0005](0005-ag-grid-filter-parity-across-backends.md): parity applies to server-side backends, and combining `infiniteScroll()` or paging with a Hazelcast backing fails generation. This is only viable for small sets, so a `maxRows` limit (default 10,000) fails population or the fetch loudly rather than truncating.

The map is derived data, never a source of truth. It is rebuilt from the database on startup (eager by default, lazy by property, globally or per Searchable DTO), and a generated rebuild service can clear and repopulate it. Because of this there is no index-style version parameter, unlike `elasticsearchEnabled(version = n)`: a new document shape is picked up by rebuilding. The client sees a snapshot as of fetch time, with no live push in v1.

Alternatives considered: pushing the cache behind the existing server-side row model (rejected: the point is client-side filtering over a small set, with no per-request query cost), and a per-Entity `cacheable {}` read cache (rejected: it caches single Entities and cannot hold denormalized, joined rows).

Multi-node clusters. Population is coordinated through the Hazelcast cluster itself, so any number of nodes sharing one cluster behave as one; all coordination state lives in IMaps and a set beside the data (`<map>__control`, `<map>__staging`, `<map>__changed`), none in a node's JVM. The protocol is one plain class, `HazelcastClusterPopulator` in `libs/maia-hazelcast`, that each generated repo calls (ordinary code, not a proxy, so consistent with ADR-0002) and that is tested once there. The mechanism is two IMap key locks on the control map plus a few typed control entries, because the CP subsystem is not available: the showcase builds its Hazelcast `Config` by hand from the defaults, which have no CP members (`cp-member-count` 0), and a CP lock needs a CP group of at least three members. IMap locks need no configuration and are released by Hazelcast when the owning member leaves the cluster. Consequences. Whether the map is populated is a cluster-wide fact: a lazy node serves what another node filled, and only one node populates at a time. A population streams the database into a staging map while viewers keep reading the previous complete set; the ids refreshed or deleted meanwhile (on any node) are re-read from the database into the staged set, mostly without holding the state lock, so none is lost and a deleted row cannot be resurrected; the staged set is then copied into the served map between two increments of a sequence number, and readers retry a read that overlapped the copy, so they see the old or the new complete set, never a mixture or an empty one. Start-up compares a document-shape stamp (a hash of the DTO's field names and types, generated per DTO) with the one stored in the control map when the map was populated: a node that finds a populated map with its own stamp leaves it alone, whether it is joining, restarting or handling a repeated context-refresh event (the start is idempotent), and a node whose stamp differs rebuilds it (eager) or marks it unpopulated so the first fetch rebuilds it (lazy), because the map is derived data and a new document shape is picked up by rebuilding. The only node of a fresh cluster finds an empty, unstamped map and populates it (eager) or leaves it for the first fetch (lazy). Failures: a population that fails (for example a transient database error) discards its staging, applies the changes recorded meanwhile to the previous set, keeps serving that set and is rethrown; a `maxRows` failure is the exception, it leaves the map empty and unpopulated for every node because no set can be served. A node that dies mid-population releases its locks, and the next node to notice (a population recorded as running with the populate lock free) marks the map unpopulated, discarding the partial work, and populates it again; its old rows stay served until the replacement is published, unless it died mid-copy, when the partial copy is cleared. The rebuild service always runs its own population, even if it waited behind another node's, so the data reflects the database as of the call; start-up and fetches that merely wait for a population already in flight do not run a second one. The populate lock has a lease, `maia.hazelcast-blotter.populate-lock-lease-seconds` (default 600): a hung populator loses the lock at the lease, a waiting caller then takes over, and a waiter that still cannot get the lock fails with `PopulationLockTimeoutException` after the lease plus a 10 second grace instead of waiting forever; the hung populator, if it wakes up, notices at its next chunk or at publication that it no longer owns the lock and fails without touching shared state (a population must finish within the lease). A short window remains and is accepted: a populator whose lease just expired can write one more chunk into the shared staging map before it notices, which could put a row of an older snapshot into the replacement population.
