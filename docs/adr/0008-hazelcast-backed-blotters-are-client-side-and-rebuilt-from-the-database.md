# Hazelcast-backed Blotters are client-side and rebuilt from the database

A Searchable DTO can be backed by a Hazelcast map, declared with `hazelcastEnabled(autoRefresh = true)`, as an alternative to SQL (the default) or Elasticsearch. The three backings are mutually exclusive on one Searchable DTO. The map holds the same rich, denormalized row as an Elasticsearch document: [ADR-0007](0007-es-backed-blotters-denormalize-entity-refs.md) applies, and the existing refresh-dependency plan keeps entries fresh after the owning transaction commits, as in [ADR-0004](0004-crud-notifications-delivered-after-commit.md).

A Hazelcast-backed Blotter is a Client-side blotter: one generated endpoint returns the whole set, and AG Grid filters and sorts it in the browser. There is no server-side filter model, paging or infinite scroll, so this is a deliberate exception to [ADR-0005](0005-ag-grid-filter-parity-across-backends.md): parity applies to server-side backends, and combining `infiniteScroll()` or paging with a Hazelcast backing fails generation. This is only viable for small sets, so a `maxRows` limit (default 10,000) fails population or the fetch loudly rather than truncating.

The map is derived data, never a source of truth. It is rebuilt from the database on startup (eager by default, lazy by property, globally or per Searchable DTO), and a generated rebuild service can clear and repopulate it. Because of this there is no index-style version parameter, unlike `elasticsearchEnabled(version = n)`: a new document shape is picked up by rebuilding. The client sees a snapshot as of fetch time, with no live push in v1.

Alternatives considered: pushing the cache behind the existing server-side row model (rejected: the point is client-side filtering over a small set, with no per-request query cost), and a per-Entity `cacheable {}` read cache (rejected: it caches single Entities and cannot hold denormalized, joined rows).

Multi-node clusters. Population is coordinated through the Hazelcast cluster itself, so any number of nodes sharing one cluster behave as one; all coordination state lives in IMaps beside the data (`<map>__control`, `<map>__staging`, `<map>__changed`), none in a node's JVM. The mechanism is two IMap key locks on the control map plus a few control entries, because the CP subsystem is not available: the showcase builds its Hazelcast `Config` by hand from the defaults, which have no CP members (`cp-member-count` 0), and a CP lock needs a CP group of at least three members. IMap locks need no configuration and are released by Hazelcast when the owning member leaves the cluster. Consequences: whether the map is populated is a cluster-wide fact, so a node that joins a populated cluster does not clear or rebuild it and a lazy node serves what another node filled; only one node populates at a time (a caller that waited for another node's population does not run a second one); a population streams the database into a staging map while viewers keep reading the previous complete set, and on completion the ids refreshed or deleted meanwhile (on any node) are re-read from the database into the staged set, so none is lost and a deleted row cannot be resurrected, before the staged set is copied into the served map (readers retry a read that overlapped the copy, so they see the old or the new complete set, never a mixture); a node that dies mid-population releases its locks, and the next node to notice that a population is recorded as running without the populate lock being held discards its partial work, so the map is not left marked populated and another node populates it; a `maxRows` failure leaves the map empty and unpopulated for every node. The only node in a cluster that starts (or whose context is refreshed again in place) still treats the map as derived data and rebuilds it. A population that hangs without its node dying holds the populate lock until it finishes.
